## Authority hierarchy (GOLDEN RULE)

BEAT operates under a layered governance hierarchy. Each layer takes precedence over those below:

```
1. CONSTITUTION (project)       → Project-specific rules (inviolable, overrides org)
2. CONSTITUTION (organization)  → Corporate rules (inviolable, baseline)
3. COLLABORATIVE MODE           → Principles, Decision Gates, Due Diligence (configurable)
4. BEAT.md (this file)          → Project context and complementary rules
5. MEMORY + INSTINCTS (project) → Project learnings (overrides org)
6. MEMORY + INSTINCTS (org)     → Organization-wide learnings (baseline)
7. Conversation instructions    → User commands in the current session
```

### Granularity principle

Constitution, Memory, and Instincts exist at **two levels**: organization (global) and project (local). **Project always overrides organization** — the more specific overrides the more generic:

- **Project Constitution** > Organization Constitution
- **Project Memory** > Organization Memory
- **Project Instincts** > Organization Instincts

Example: if the org Constitution says "use PostgreSQL" but the project Constitution says "use SQLite", SQLite wins. The level closest to the code is the most precise.

### Practical implications

- If a conversation instruction contradicts BEAT.md → BEAT warns and waits for decision
- If BEAT.md contradicts Collaborative Mode → Collaborative Mode prevails
- If Collaborative Mode contradicts Constitution → Constitution prevails
- Within each system, **project overrides organization**
- BEAT **never** silently violates a higher layer — always reports the conflict

## BEAT systems (quick reference)

### Constitution

Inviolable rules that define absolute limits for security, compliance, and governance. Exist at two levels:

- **Organization** (global): corporate rules that apply to all projects
- **Project** (local): project-specific rules — **override organization rules**

BEAT consults both levels automatically, resolving conflicts by the granularity principle (project > org).

### Collaborative Mode

Configurable quality governance system via `nt-beat.json` or settings panel. Controls:

- **Quality principles** (12 principles in 4 groups):
  - Architecture: SOLID, DDD, Screaming Architecture, Separation of Concerns
  - Simplicity: KISS, YAGNI, DRY
  - Workflow: SDD (Spec-Driven Development), TDD (Test-Driven Development)
  - Quality: Clean Code, Immutability, Fail Fast
- **Decision Gates** (8 categories where BEAT pauses and presents options before deciding):
  - Architecture, Security, Technology, Database, API Design, Infrastructure, Testing, UX/UI
- **Due Diligence** (mandatory 8-item checklist before declaring work complete):
  - Spec Compliance, Integration (Anti-Ghost-Code), Immutability, Security, Type Safety, Dead Code, Error Handling, Project Rules
  - Requires **observable proof** (grep output, typecheck output, test results)
- **Interview Mode** (structured interview for spec creation via `/spec`)

> **IMPORTANT**: Collaborative Mode principles and rules are already active by default. This BEAT.md does NOT need to repeat them — only reinforce project-specific priorities or override defaults when necessary.

**Useful commands:**
- `/spec` — create spec via Interview Mode
- `/due_diligence` — force a due diligence review
- `/review` — review pending changes

### CBI (Codebase Intelligence)

Automated codebase analysis via knowledge graph. BEAT uses CBI for:

- Grounding Interview Mode questions in actual code (do not ask what it already knows)
- Pre-implementation validation: change impact, dependencies, affected files
- Integration verification: detect ghost code (modules that compile but nobody uses)
- Diff analysis: change risk, suggested tests

**Commands:**
- `nt-beat cbi` — analyze codebase
- `nt-beat cbi chat` — Q&A about the codebase
- `nt-beat cbi diff` — change impact analysis

> If CBI is available, BEAT uses it automatically. If not, it degrades gracefully to grep/read.

### Memory + Instincts

Two cross-session learning systems, each at two levels:

- **Memory**: explicit learnings (the user asks to remember)
  - *Organization*: learnings that apply to all projects
  - *Project*: learnings specific to this project — **override org**
- **Instincts**: patterns learned automatically from interactions (growing confidence)
  - *Organization*: general user patterns
  - *Project*: patterns specific to this project's context — **override org**

BEAT consults both at the start of each session. High-confidence instincts influence behavior; low-confidence ones are suggestions. When a project instinct contradicts an organization instinct, the project one prevails.

### Spec Lifecycle

BEAT manages specs via the `spec` tool (register, update, close, list, activate, assign):

- Specs are registered in the index (`index.json`) with metadata: progress, branch, commit, criteria
- SHA-256 content hash detects external edits
- Automatic pre-implementation validation: git diff, criteria vs code, branch mismatch
- Due Diligence gate: `close` is blocked if DD was not executed
- Cross-session resumption: when opening BEAT, it knows where it left off
